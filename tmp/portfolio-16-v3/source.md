# Look-See-Do Fighter

**AI 협업을 통한 Photon Quantum 3 기반 격투 게임 리팩터링 및 개발 자동화**

개발을 중단했던 2D 온라인 격투 게임을 다시 분석하고, 기존 전투 콘텐츠를 보존하면서 결정론적 아키텍처와 게임플레이를 개선한 프로젝트입니다.

**기존 게임을 완성하는 것뿐 아니라, 개발 방식 자체를 개선하는 것을 목표로 설정했습니다.**

Look-See-Do Fighter는 Photon Quantum 3를 이용해 제작하던 2D 격투 게임입니다. 기존 프로젝트에는 기본 전투, 공격 기술, 애니메이션 및 네트워크 구조가 구현되어 있었지만, 일부 실행 상태가 공유 에셋이나 로컬 데이터에 의존하는 등 결정론적 설계 관점에서 개선할 부분이 존재했습니다.

또한 전투 기능을 확장하는 과정에서 공격별 중복 코드, 복잡한 애니메이션 전이, 반복적인 수동 검증이 유지보수 부담으로 작용했습니다.

**개발 목표**

1. **구조적 안정성 확보:** Quantum Simulation과 Unity View의 책임을 명확히 분리

3. **게임플레이 확장:** 선입력, 3선승, 공중 콤보 및 전투 연출 개선
4. **AI Native 개발 체계 구축:** Skills, Hooks, MCP, 테스트 및 버전 관리 절차 표준화

**개발 접근 방식**

기존 코드 분석 → 결정론적 구조 정리 → 콘텐츠 리팩터링 → 게임플레이 확장 → 플레이 오류 해결 → 자동 검증 및 기록

### Slide 03. 게임 기획 및 핵심 시스템

# 기술 커스터마이징과 프레임 단위 심리전에 집중한 2D 격투 게임

Look-See-Do Fighter의 핵심은 플레이어가 사용할 기술을 직접 구성하고, 공격의 발동·지속·회복 프레임과 상호작용을 이해해 상대방과 심리전을 펼치는 것입니다.

**01. 기술 커스터마이징**

- 방향 7개 × 공격 버튼 4개, 총 28개의 기술 슬롯
- 슬롯별 3개의 기술 선택지
- 기술별 비용을 기준으로 한 예산 제한 시스템
- 기본 예산 140을 활용한 로드아웃 구성

**02. 프레임 기반 전투**

- 공격 발동·지속·회복 프레임
- 상단·중단·하단 공격 판정
- 가드, 패링, 카운터 및 경직 처리
- 거리와 공격 타이밍에 따른 기술 상호작용

**03. 온라인 매치**

- Photon Quantum 3 기반 입력 동기화
- 라운드별 HP 및 전투 상태 초기화
- 3승 선취 매치 진행
- KO, 동시 KO 및 최종 결과 판정

**기획 의도**

복잡한 조작을 반복하는 것보다, 제한된 기술 구성과 프레임 단위 선택에서 전략적 깊이가 발생하는 격투 게임을 지향했습니다.

### Slide 04. 기술 아키텍처

# 결정론적 Simulation과 Unity View의 책임 분리

**네트워크 게임에서 중요한 것은 모든 클라이언트가 동일한 입력과 상태를 기반으로 같은 전투 결과를 계산하는 것입니다.**

Photon Quantum 3의 ECS 및 Frame 기반 구조를 사용하고, 로컬 설정과 게임플레이 판정 및 시각적 표현이 서로의 역할을 침범하지 않도록 설계했습니다.

| 계층 | 주요 책임 |
|---|---|
| Unity Local | 메뉴, 기술 선택, PlayerPrefs, 입력 수집 |
| RuntimePlayer | 플레이어별 로드아웃 및 연결 데이터 전달 |
| Quantum Frame | HP, 상태, 입력 버퍼, 콤보, 라운드 진행 |
| Quantum Systems | 이동, 공격 판정, 피격, 전투 상태 전환 |
| Unity View | Animator 표현, HUD, VFX, 카메라 및 사운드 |

**설계 원칙**

- 전투 결과에 영향을 주는 값은 Quantum Frame에서 관리
- 여러 플레이어가 공유하는 공격 설정은 불변 데이터로 취급
- 게임 로직에서는 FP 및 정수 tick 기반 계산 사용
- Unity의 시각적 상태가 실제 전투 결과를 결정하지 않도록 분리
- 기존 Quantum Animator 및 시스템 실행 순서를 보존

**기술적 의의**

롤백 과정에서 복원되어야 하는 상태와 화면에서만 필요한 표현 상태를 구분하여, 네트워크 동기화와 기능 확장에 대응할 수 있는 구조로 개선했습니다.

### Slide 05. 핵심 리팩터링 ① — 상태 소유권

# 로컬 데이터와 공유 에셋에서 결정론적 게임 상태 분리

**Problem**

기존 플레이어 스폰 과정에서는 각 클라이언트의 PlayerPrefs에서 기술 설정을 직접 읽는 경로가 존재했습니다.

또한 잽 연계의 예약 상태인 `BufferedNextAttack`이 여러 플레이어가 공유할 수 있는 Window Event 에셋에 저장되어 있었습니다.

이 구조는 로컬 저장 데이터와 플레이어별 실행 상태가 Quantum의 입력 및 Frame 관리 경계를 우회할 수 있다는 문제가 있었습니다.

**Solution**

**1. 로드아웃 전달 구조 개선**

`PlayerPrefs → 로컬 검증 → RuntimePlayer → AddPlayer → Quantum Frame`

- 기술 ID·슬롯 수·비용 검증
- 플레이어별 로드아웃을 RuntimePlayer에 복사하여 전달
- Simulation에서 `f.GetPlayerData()`로 접근
- 반복 AddPlayer 시 중복 생성 및 상태 초기화 방지

**2. 실행 상태 소유권 재설계**

- `BufferedNextAttack`을 공유 에셋에서 플레이어 Frame 컴포넌트로 이관
- 호출마다 계산 가능한 임시 상태는 지역변수로 전환
- 공격 수치와 설정은 불변 AssetObject로 유지
- FP 기반 애니메이션 프레임 환산 로직 정리

**Result**

각 클라이언트의 로컬 선택, 여러 엔티티가 공유하는 설정, 롤백 시 복원할 게임 상태를 명확하게 구분했습니다.

서로 다른 로드아웃과 반복 AddPlayer, 입력 재생 및 Frame 복원 시나리오를 포함한 후속 테스트에서 관련 동작을 검증했습니다.

### Slide 06. 핵심 리팩터링 ② — 공격 시스템

# 37종 공격의 판정 계약을 유지하면서 중복 구조 제거

**Problem**

기존 전투 시스템은 공격마다 피해량, 경직, 피격 높이, 히트박스 생성 등의 코드가 중복되어 있었습니다.

그러나 단순히 공통 클래스로 합치면 공격별 타격 타이밍, 특수 동작, Animator 연결 및 직렬화된 에셋 참조가 변경될 위험이 있었습니다.

**Solution**

공격 데이터와 히트박스 생성 책임을 분리하고, 공격별 고유 동작은 기존 이벤트에 유지하는 구조를 선택했습니다.

| 구성 요소 | 담당 역할 |
|---|---|
| LSDFSingleHitDefinition | 단타 피해·경직·판정 데이터 |
| LSDFTimedHitDefinition | 다단히트 생성 프레임과 타격 데이터 |
| LSDFHitboxFactory | Collider·Hitbox·파괴 tick 생성 |
| 기존 Window Event | 이동, 연계, 특수 동작 및 종료 처리 |

**점진적 적용**

왼어퍼 1종 → 잽 4종 → 다단히트 2종 → 나머지 30종

한 번에 모든 공격을 변경하지 않고 대표 유형의 동작 계약부터 확인하며 총 37종의 구조를 이관했습니다.

**보존한 항목**

- 기존 공격별 생성 프레임과 피해·경직 수치
- 타입명, GUID, Asset ID 및 Animator 참조
- 다단히트 타이밍과 개별 공격의 특수 처리
- 좌우 반전 및 생성·파괴 tick 경계

**Result**

중복된 공격 생성 절차를 공통화하면서도 기존 공격 콘텐츠와 직렬화 참조를 보존하는 방향으로 리팩터링했습니다.

구조 개선 과정에서 가장 중요하게 판단한 기준은 단순한 코드 축소가 아니라 **기존 게임플레이 계약을 유지하는 것**이었습니다.

### Slide 07. 핵심 기능 ① — 입력 버퍼

# 프레임 단위 선입력 시스템 구현

**Problem**

공격이나 피격으로 행동이 잠겨 있을 때 입력한 기술을 다음 행동으로 연결하려면 입력을 일정 시간 보존해야 했습니다.

하지만 Quantum Animator의 명령 전달은 여러 tick에 걸쳐 진행되므로, 단순히 버튼 입력을 짧게 저장하면 애니메이션 상태 전이 도중 명령이 사라질 수 있었습니다.

**Solution**

입력의 대기 상태와 Animator에 전달된 상태를 분리한 Frame 기반 입력 버퍼를 구현했습니다.

**동작 방식**

1. 버튼이 새롭게 눌리는 순간 방향·버튼·입력 tick 저장
2. 행동 잠금 중에는 최신 명령 1개만 대기
3. 행동이 가능해지는 첫 명령 처리 tick에 전달
4. Animator가 전달된 명령을 처리할 때까지 별도 유지
5. 유효시간 초과, KO 및 라운드 전환 시 버퍼 정리

**주요 설계 판단**

- 실제 게임 설정의 선입력 허용 범위: 20tick
- 새 객체의 초기 기본값: 10tick
- 버튼 홀드로 유효시간이 무한히 갱신되지 않도록 처리
- 입력 후 방향 변경이나 버튼 해제가 저장 명령을 바꾸지 않도록 구성

**Verification**

후속 157개 전체 테스트 PASS.

Photon 온라인 검사에서 입력 tick 384에 기록된 명령이 tick 392에 전달되는 동작을 확인했습니다.

이는 해당 잠금 시나리오에서의 정상 전달 관측값으로, 전체 평균 입력 지연을 의미하지 않습니다.

### Slide 08. 핵심 기능 ② — 라운드 및 매치

# 단일 KO에서 3선승 매치 시스템으로 확장

**Problem**

기존 게임은 KO 이후 하나의 전투 결과에 머무는 형태였습니다.

정식 매치 흐름을 구성하려면 라운드 종료, 상태 초기화, 다음 라운드 시작 및 최종 매치 종료까지 하나의 규칙으로 연결해야 했습니다.

**Solution**

Quantum Frame의 게임 상태를 중심으로 라운드 및 매치 전환 로직을 구현했습니다.

**Match Flow**

`WaitingForPlayers → Intro → Fighting → RoundEnd → Intro / MatchEnd`

**주요 구현**

- KO 결과를 한 번만 확정하여 중복 처리 방지
- 양쪽 동시 KO는 무득점으로 동일 라운드 재시작
- 라운드 전환 시 HP·위치·공격·버퍼·콤보 상태 초기화
- 승수와 기술 로드아웃은 라운드 사이에 유지
- 결과 120tick, 인트로 150tick 기반 진행
- 먼저 3승을 달성한 플레이어가 매치 승리
- verified 매치 종료 조건에서 연결 종료 및 메인 화면 복귀

**Verification**

실제 Photon 테스트에서 KO 5회, 라운드 초기화 및 인트로 4회, 최종 3:2 매치 결과와 verified Frame 진행을 확인했습니다.

메인 화면 복귀는 이후 별도로 구현하고 사용자 테스트로 확인했습니다.

**설계 의의**

화면의 코루틴이 라운드 결과를 결정하는 대신 Quantum Simulation이 전투 진행의 기준 상태를 관리하도록 했습니다.

### Slide 09. 핵심 문제 해결 ① — 공중 콤보 피해

# 실제 타격 횟수와 애니메이션 진입 횟수의 불일치 해결

**Problem**

공중 콤보 중 일부 타격에서 피해가 적용되지 않는 문제가 발생했습니다.

기존 피해 공식은 `LSDF_Player.hitCount`를 참조했지만, 이 값은 실제 공격이 적중한 횟수가 아니라 Air 애니메이션에 진입한 횟수였습니다.

공중 피격 전이 구조가 변경되면서 두 값이 서로 달라질 수 있었고, 특정 카운트에서 피해가 0으로 처리되는 기존 분기가 문제를 드러냈습니다.

**Root Cause**

- 기존 기준: Air 애니메이션 진입 횟수
- 실제 필요한 기준: 공중 콤보의 타격 접촉 횟수
- 두 값이 다른 의미임에도 동일한 전투 계산에 사용

**Solution**

`LSDF_AirCombo.HitCount`를 실제 피해 계산의 기준으로 변경했습니다.

`Juggle.OnHit → Combo HitCount 갱신 → ApplyHit 피해 계산`

공중 후속타에는 다음의 피해 배율을 적용했습니다.

| 타격 | 피해 배율 | 기본 피해 20 기준 |
|---|---:|---:|
| 지상 시동기 | 100% | 20 |
| 공중 후속 1타 | 70% | 14 |
| 공중 후속 2타 | 50% | 10 |
| 공중 후속 3~5타 | 30% | 6 |

정수 계산을 이용해 피해 처리의 결정론적 성질을 유지하고, 곱셈 중간 오버플로 가능성도 고려했습니다.

**Verification**

최초 관련 테스트 110개 중 109개 PASS, 통합 테스트 1개 FAIL.

프로젝트에서는 다섯 가지 전용 Skill을 구성해 서로 다른 개발 작업의 절차와 검증 기준을 관리했습니다.

- 프로젝트 루트와 공통 개발 지침 탐색
- 컨텍스트 재개 및 압축 이후 작업 규칙 안내
- 정적 검사기 진입점 연결
- 실제 코드와 최신 작업 문서를 기준으로 작업 재개

**Quantum 정적 정책 검사기**

`quantum_guard.py`를 이용하여 Simulation 코드에서 다음과 같은 위험 패턴을 조사합니다.

- PlayerPrefs 등 로컬 데이터 직접 접근
- FP에서 float로의 변환 및 비결정론적 연산 패턴
- 게임 판정 영역에서의 부적절한 Unity API 사용
- 비결정적 시간·난수·스레딩 관련 사용
- 알려진 공유 가변 상태 패턴

**설계 원칙**

Skill은 작업 절차를 정의하고, Hook은 특정 이벤트에서 실행되며, 테스트는 실제 동작을 검증합니다.

세 기능을 구분함으로써 AI의 판단과 자동 검증의 책임을 명확히 했습니다.
