# 검증 절차와 증거 기준

## 검증은 작업마다 한 차례

조사와 구현을 끝낸 뒤, 변경 범위에 필요한 검사만 골라 하나의 최종 검증 묶음으로 한 번 실행한다.
같은 명령/시나리오를 반복하지 않는다. 여러 스킬을 사용해도 검증 묶음을 각각 만들지 않는다.
실패해도 자동 재실행하지 않는다. 수정했다면 `수정 후 미검증`을 표시한다. 재실행은 사용자 별도 요청에 따른다.
검사 자체에 필요한 복수 사례나 두 재생의 체크섬 비교는 단일 검사 내부 절차로 묶고, 그 묶음을 반복하지 않는다.
사전 실행 재현으로 이미 한 차례를 사용했다면 이후 구현은 미검증 상태로 보고한다.

## 최종 검증에서 고를 명령

프로젝트 루트에서 Python 3.10 이상과 Git을 사용한다. 도구는 외부 패키지가 필요 없다.

| 변경 범위 | 선택할 검사 |
|---|---|
| 시뮬레이션 | `python tools/ai/quantum_guard.py check` |
| 전체 부채 목록 조사 자체가 요청됨 | `python tools/ai/quantum_guard.py audit` (check와 중복 실행하지 않음) |
| 검사기/훅 구현 | `python -B -m unittest discover -s tools/ai/tests -v` |
| 문서/스킬 | 수정한 문서 링크·스킬 형식 확인 |
| 변경 diff | `git diff --check` |

`git status`와 소스 탐색은 변경 범위를 파악하는 읽기 작업이다. 위 검사를 습관적으로 전부 실행하지 않는다.

`check` 종료 코드: 0=기준선 대비 신규 패턴 없음, 1=신규 발견, 2=검사 오류.
`audit`는 전체 목록을 표시할 뿐 통과 여부를 판정하지 않는다.
검사는 사용자 Simulation C#만 읽는다. Vendor/Generated, View, QTN, 프리팹 의미 검증은 포함하지 않는다.
Q006은 초기 감사에서 찾은 필드명만 탐지한다. 다른 이름의 공유 가변 상태, alias, reflection, 조건부 컴파일,
보간 문자열 내부 표현식 등의 의미를 보증하지 않는 어휘 기반 검사다.

## 변경별 필요한 검사

| 변경 | 필요한 검증 |
|---|---|
| 문서/스킬 | 상대 링크·경로·frontmatter, 명령 실존과 실행 결과 |
| 훅/검사기 | 격리 fixture에서 신규 위험 탐지, 기존 부채 허용, 제외 경로, 오류/반복 Stop 동작 |
| C# 시뮬레이션 | Unity 컴파일 + 관련 전투 시나리오 + 아래 결정론 검사 |
| QTN/RuntimePlayer | 생성/직렬화, 기존 프로토타입/asset 참조, 두 플레이어 전달과 재접속 |
| 공격/시스템 순서 | 입력 소비 tick, 첫 활성 hitbox tick, 물리 관측 tick, 파괴 tick, 다단히트 수 |
| View/UI | 입력 매핑, 두 로컬 시점, 재진입/재접속, 구독 중복/취소, Runner 범위 |

## Unity MCP 운영

1. 프로젝트 정보와 `manage_scene(action="get_active")`로 대상 확인. 다중 인스턴스면 해당 프로젝트를 지정한다.
2. 기존 오류는 이미 확보한 로그를 참고하고, 최종 검증에서 `read_console(action="get", types=["error","warning"])`로 결과를 한 번 확인한다. `clear`하지 않는다.
3. QTN 변경 시 설치된 CodeGen 설정/메뉴를 먼저 확인하고 생성한다. 생성 파일만 수작업 수정하지 않는다.
4. 한 번 시작한 컴파일/검사의 완료를 기다리고 결과를 확인한다. 완료 대기는 재실행이 아니다. 콘솔에 오류가 없다는 것만으로 테스트 통과라고 하지 않는다.
5. 테스트 도구가 비동기 job을 반환하면 최종 결과까지 확인한다. 발견된 테스트 0개는 테스트 성공의 증거가 아니다.

현재 씬을 바꿔야 하는 검사는 그 시점의 미저장 상태와 사용자의 실행 범위를 확인한다.
같은 프로젝트를 이미 연 Unity와 별도 batchmode 인스턴스로 동시에 열지 않는다.
CI 게임 테스트는 유효한 Unity 라이선스, Quantum SDK, 독립 checkout/runner와 실제 테스트 진입점을 마련한 후 연결한다.
이 세팅에는 가상의 Unity 테스트 클래스/`-executeMethod` 명령을 넣지 않았다.

## 전투 회귀 매트릭스

| 시나리오 | 관측할 것 |
|---|---|
| 1P/2P 방향·동시 좌우·앉기·패링 | 좌우 반전, 방향 우선순위, 잘못된 Up/Down 동시 입력 |
| 대시 이중 입력 경계 | DashInputWindow 직전/경계/직후 결과 |
| 상/중/하단 + 서기/앉기/점프 | 가드/회피/피격 분기 및 지속시간 |
| 일반/카운터/런처/벽 | HP, DelayFrame, hitCount, wallCount, hitbox 소유자 |
| Jap 연타, 같은 스킬 동시 사용 | 플레이어 간 버퍼 누출, 시작/중단/종료 틱 |
| NarakTwo/LarsCutKick | 각 hitbox 1회 생성·피격·파괴, 중간 취소 |
| 라운드 종료/동시 KO/재접속 | loseRound 증가 횟수, 잠금/회복, 재스폰과 결과 표시 |
| 서로 다른 스킬 저장값 | 각 PlayerRef의 28개 ID와 모든 클라이언트 Frame의 일치 |

기존 동작의 버그를 고칠 때는 기존 결과와 목표 결과를 구분해 fixture를 작성한다.

## 결정론 검증

같은 실행 버전의 build/commit, Quantum SDK, runtime/session config, asset DB, seed,
플레이어 payload와 입력 기록을 고정한다. 연속 실행/재생 두 번의 같은 verified tick 체크섬을 비교한다.
별도로 입력 지연/rollback을 유발하고 재시뮬레이션 이후 같은 verified tick의 결과를 비교한다.
한 번의 로컬 플레이나 같은 컴퓨터에서의 정상 실행만으로 cross-platform determinism을 입증하지 않는다.
구조 변경 전후는 직렬화 레이아웃 차이로 raw checksum이 달라질 수 있으므로 tick·HP·피격 횟수 같은 동작 지표를 함께 비교한다.

## 기존 부채 기준선 관리

`tools/ai/quantum-baseline.json`은 파일·규칙·정규화 코드 해시별 허용 횟수다.
공백/주석/행 이동만으로 새 부채가 되지 않고, 같은 위험 코드의 추가 복제는 잡는다.
기존 같은 줄 주변의 의미 변경은 놓칠 수 있다. 의미 검토와 결정론 테스트는 필수다.
수정이 끝난 항목은 기준선에서도 삭제해 재도입을 막는다.
`python tools/ai/quantum_guard.py baseline-candidate`는 후보 JSON을 stdout으로만 출력한다.
자동 덮어쓰기 기능은 없다. 기준선 증가는 근거와 리뷰 없이 적용하지 않는다.
